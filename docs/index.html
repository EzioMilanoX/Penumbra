Penumbra

Dois seres que não podem se tocar e não avançam separados. O mundo não tem um chão: tem dois, e eles se excluem — cada célula de éter é piso sólido para exatamente um deles, decidido pela luz naquele instante.

A escala

Tudo depende de um número por célula

O campo de luz vai de 0 a 1 em cada célula da grade. Três limiares o cortam, e é da ordem deles que o jogo inteiro depende: entre 0.12 e 0.60 existe uma penumbra onde os dois sobrevivem. Sem essa faixa, toda célula mataria um deles e nenhuma fase teria solução — por isso o carregador de dados recusa um arquivo que inverta essa ordem.

A morte nunca é instantânea. Um medidor sobe enquanto o perigo dura e desce quando passa — 1,3 s para a Lumen, 1,6 s para a Umbra. Atravessar correndo uma nesga da polaridade errada é uma decisão possível, e é isso que dá às habilidades a função de ferramenta em vez de interruptor.

Os dois seres

Simétricos na estrutura, opostos no valor

Um único sistema comanda os dois. Toda a assimetria vive nos números do arquivo de dados — se ela virasse dois sistemas duplicados, a próxima regra nova precisaria ser escrita duas vezes e poderia divergir num dos lados sem ninguém notar.

O que a altura do salto esconde

O que decide se um degrau é subível não é alcançar a altura dele — é quanto tempo o ser fica lá em cima. Subir exige ao menos uma célula de deslocamento horizontal, porque o topo do degrau nunca está na coluna que o ser ocupa. A Umbra alcança 2,45 células de altura, mas a duas células ela desloca apenas 1,43 coluna — pouco mais que a única que subir exige, e nem chega a três. A Lumen alcança 3,27 e ainda desloca 1,57 lá em cima. É por isso que penumbra/reachability.py existe, e é isso que um teste mede em cada fase.

O alfabeto

Sete terrenos, uma pergunta cada

Cada fase é um arquivo de texto de 28 × 17. O que muda entre os terrenos não é o visual — é de quem é o chão, e sob que condição.

A última linha da grade é sempre vazia: é o abismo. O motor trata fora-dos-limites como sólido, então sem essa linha ninguém cairia de verdade — o ser simplesmente pousaria na borda de baixo da tela.

As doze fases

Cada uma ensina uma coisa e só uma

As miniaturas abaixo são desenhadas a partir do ASCII real de cada fase, lido do mesmo arquivo que o jogo carrega — não são capturas de tela que envelheceriam no primeiro ajuste de nível.

Arquitetura

Dois chãos na mesma simulação

É o ponto não-óbvio do projeto. O TileCollisionSystem da engine resolve toda entidade com Transform + Velocity + Hitbox contra uma grade — mas os nomes das três pools são parâmetros do construtor. Então Penumbra cria uma segunda pool de hitbox e registra dois TileCollisionSystem: um contra a grade da luz, olhando só quem tem hitbox; outro contra a grade da sombra, olhando só quem tem hitbox_shadow.

Nenhum dos dois sabe que o outro existe, e nenhum sistema genérico da engine ganhou um ramo condicional. O campo de luz reescreve as duas grades a cada frame — e é só isso que faz a ação de um ser desfazer o terreno do outro.

Ordem dos sistemas por frame — e por que ela é essa

  1. PhysicsSystem — integra posição (engine)
  2. CollisionSystem — ocioso aqui: só a Lumen tem hitbox
  3. TileCollisionSystem — Lumen contra a grade da luz
  4. TileCollisionSystem — Umbra contra a grade da sombra
  5. GravitySystem — fecha o contrato Physics → Tile* → Gravity
  6. DualityControlSystem — escreve velocity depois de tudo acima, a única posição válida para input
  7. LightFieldSystem — recalcula a luz e as duas grades
  8. WorldClockSystem — farol e eclipse: o que muda sozinho
  9. CrustBreakSystem — o verbo da Umbra; muta o terreno
  10. PolarityDoorSystem — lê a luz deste frame
  11. OutcomeSystem — lê posições já resolvidas
  12. PresentationSystem — só pixels; removível sem mudar o jogo

Não há sistema de "sair". ESC é tratado nas cenas — recua uma tela por vez e só encerra no título — porque um sistema só roda dentro de world.step(), e o menu existe justamente enquanto o mundo está parado.

Como a luz se propaga

Um flood geodésico de 8 vizinhos, relaxado 10 vezes por frame sobre a grade 28 × 17. Cada passe empurra a luz uma célula, perdendo 1/7 de intensidade; as diagonais custam √2 a mais. Uma fonte de intensidade I deixa sólido tudo num raio geodésico de (I − 0.35) × 7 células, contornando rocha. Na prática: uma lâmpada alcança 4,55 células, a Lumen fica segura até 6,16 dela, e a Umbra se dissolve dentro de 2,8.

As diagonais não são cosméticas. Só com os 4 vizinhos ortogonais a distância resultante é a de Manhattan, e uma lâmpada acende um losango — com alcance diagonal a ~71% do horizontal. Nenhuma fase deste jogo teria sido desenhável assim.

Rodar

A engine vive no repositório dela

git clone https://github.com/EzioMilanoX/OuroborosEngine.git
git clone https://github.com/EzioMilanoX/Penumbra.git

pip install -e ./OuroborosEngine        # numpy + pygame-ce vêm com ela
cd Penumbra && python -m penumbra.main  # sempre da raiz, como módulo

pytest -q                      # 108 testes headless
python -m tools.audit_levels   # luz, sobrevivência e alcance por fase

python -m não é preferência de estilo: os imports são absolutos e os caminhos de config.json são relativos à raiz, então python penumbra/main.py falha.

Duas maneiras de uma fase ser insolúvel

Cada uma tem seu guardião, porque nenhuma das duas gera erro em runtime — a fase carrega, o jogo abre, e ela simplesmente não pode ser terminada.

FalhaSintomaGuardião
Polaridade o éter não acende onde precisa; o facho vaza até a zona de sombra e a porta nunca abre test_shipped_levels.py
Geometria o degrau é alto demais; há um bloco sobre a cabeça e o salto morre no teto; a descida é de mão única test_reachability.py

Os testes rodam a simulação real: o mesmo World, os mesmos sistemas, na mesma ordem que o jogo com janela — só sem renderer, input e áudio concretos. Nenhum teste reimplementa uma regra para depois conferi-la contra si mesma. Os mais fortes terminam fases jogando, com um controlador rudimentar que segura as teclas na ordem certa.
